# 開源套件版本查核

在標記套件異動的路徑已審查前，逐項確認固定版本、上游問題與專案用法。已完成查核及確實需要人工確認的項目都要保存。

## 確認本次請求的離線設定

固定證據就緒後，從首次成功的 `start` 回應讀頂層 `no_fetch`。成功重送時，從完整狀態讀 `inputs.no_fetch`。續作同一已接受請求，或成功的啟動回應摘要化或缺少布林旗標時，用同一 `runtime_root`、`request_id` 執行 `status --summary` 讀頂層旗標。大型啟動摘要可從 `continue` 取得請求位置。`start` 回傳錯誤時停止該次啟動的查證。變更 `--no-fetch` 設定須建立新請求。

明確指定 `--no-fetch` 時，全程使用本機證據。其餘請求只有在確認旗標為布林 `false` 且會話可使用 Web Search 時，才查詢公開套件登錄資料、授權及上游問題。旗標為 `true`、無法核實或搜尋工具不可用時，使用本機證據完成可做的查核。

## 辨識實際異動

1. 從所選 Repo 的固定相依宣告、版本與來源設定、鎖定檔辨識套件管理方式。用 `merge-base → head` 找分支變更，並檢查合併預覽中與版本解析相關的變更。以固定 `base → merge-preview` 的相依關係確認這次合併實際影響的套件與版本。預覽有衝突或無法取得時，保留既有審查缺口，將可做的查核標明適用的分支與版本。
2. 按專案、目標框架、平台或適用的相依群組解析版本。先讀專案採用且與宣告一致的鎖定檔，再依套件管理器的語意確認精確宣告。範圍、浮動或互相矛盾的宣告與鎖定檔影響判斷時，列出待確認的實際版本。NuGet 的 `Version="1.2.3"` 是最低版本條件，`Version="[1.2.3]"` 才要求精確版本。 [NuGet 版本規則](https://learn.microsoft.com/en-us/nuget/concepts/package-versioning#version-ranges)
3. 查核新增、移除與升降版的直接相依，也查鎖定檔確認有實際版本異動的間接相依。移除時沿相依鏈核對合併後是否仍引入該版本。遇到純格式變動或可證明有效相依與版本相同的宣告變動，即完成本機核對。
4. 先讀固定來源設定與工作區套件宣告。允許對外查證時，才以公開套件登錄資料及上游授權核對已辨識的公開來源。自研或已知非開源套件沿用本機審查。內部鏡像或本機副本須能對應到所用版本的公開上游才納入。來源不明或同名來源無法分辨時，記錄人工核對項。對外只使用已確認公開的套件識別、版本及公開 API 名稱。

## 查證上游問題及專案用法

1. 允許對外查證時，由執行審查的 agent 用會話提供的 Web Search 查詢所有適用的新舊版本，新增查新版、完全移除查舊版。升降版也核對變更區間的發布說明。搜尋上游 Issue、回歸及相容性變更，開啟原文核對受影響的版本範圍、觸發條件及已發布的修復版本。只有宣告範圍時，可先查公開的版本條件與上游受影響範圍，把尚待核實的實際版本交人工確認。同一公開上游套件與版本組合在同一請求共用查詢，按各專案實際用法判定。
2. 讀取固定版本的呼叫端、設定及環境條件。間接相依沿引入它的父套件和實際使用路徑核對。對照基礎版本及本次有效變更，確認問題在合併後是否新出現，以及既有 workaround 或版本變更是否避開問題。Issue 關閉狀態與待發布的修補都須回到實際發布版本核對。
3. 本次變更新引入且可由固定證據證明會觸發的問題，寫入 `findings` 並依實際影響定 P0–P3。`evidence` 包含相依變更及證明觸發的固定 Git 行段，`evidence_summary` 附支持版本和條件的上游連結。建議核對已發布的修復版或官方避開方案，並給出適用於專案的驗證方式。靜態推導標示 `code-derived`。
4. 在 `scope_notes` 記錄每組已查證的版本、適用專案或目標、查詢日期、結論與官方來源。已避開時寫明修復版、配置或呼叫條件。基礎分支已有的相同問題記錄於查核說明。搜尋完成而未見相關候選時寫「未查到相關問題」，並註明查過的上游來源。

## 待人工確認與續作

- 先補查可取得的必要資料。仍需上游證據，或套件來源、實際版本、上游受影響範圍或觸發條件無法查清時，建一筆 `pending_confirmations`。用 `related_changes` 指向所選 Repo 的固定相依變更，說明缺少的證據及人工應核對的版本、上游問題或專案用法。依本次實際原因記錄，例如「本次審查指定 `--no-fetch`」、「無法確認本次請求的離線設定」或「本次會話無法使用 Web Search」。合併預覽等必要 Git 缺口沿用既有審查規則。
- 續作先讀完整草稿與 checkpoint，逐項核對尚待查證的版本。補齊證據後依上節保存結論與來源，從 `pending_confirmations` 與 `checkpoint.open_questions` 移除對應項目。部分查證完成時，更新目前的受阻原因、缺少的證據及人工核對方式。保留其他未決項及順序，從 `Q-001` 連續重編並更新 checkpoint 內的編號引用。
- 精簡草稿在同一次 `author` 保存查證結論、完整的 `pending_confirmations` 與 checkpoint。保存 `scope_notes` 時保留其他查證摘要，checkpoint 沿用其他已完成的操作、待讀證據及待查項。使用與所讀內容對應的 `expected_draft_sha256` 和 `expected_checkpoint_revision`。任一版本衝突時重讀完整草稿與 checkpoint，再組合更新。全部解決時以 `[]` 替換待確認清單。v3 草稿沿用相同清單規則。完成可做的檢查後，依 `check` 的最新結果用 `finish` 發布報告。

## 範例
