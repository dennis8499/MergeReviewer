# Merge Reviewer 品質驗收案例

這些案例驗證 Skill 是否找對問題、避免誤報，也確認它不會把未檢查的路徑說成已完成。它們是人工 Skill 評估案例，不是 Git helper 的單元測試；CI 目前只驗證固定 Git context、證據引用和報告一致性。

## 執行方式

1. 在系統暫存目錄建立一次性 Git repository，依案例建立共同起點、`main` 和 `feature` 分支。每個案例獨立執行，避免前一案例的物件或報告影響後一案例。
2. 以 Merge Reviewer 執行 `main` 對 `feature` 的合併模式審查，保留 manifest 和 context bundle，讓 Skill 依規則逐檔檢查並產生 Markdown 報告；若要逐項檢查結構化 JSON 結果，明確加上 `輸出JSON`。
3. 將 finding、來源 SHA、路徑、行號、覆蓋狀態、結果狀態與合併建議逐項對照標準答案。報告驗證器成功只代表結構與證據可查，不代表 Skill 找對了問題。
4. 記錄漏報、誤報、嚴重度偏差和沒有證據的引用；案例全部符合標準答案才通過人工驗收。

## 案例 1：Merge commit 解衝突時遺失訂單授權

**建置情境：**共同起點的 `capturePayment(orderId)` 尚未檢查訂單擁有者。`main` 新增 `requireOwner(currentUser, orderId)`，並有測試拒絕其他帳號的訂單。`feature` 將付款送到新的支付服務，但仍缺少 owner 檢查。將兩邊合併時，手動解衝突選了 feature 的付款流程，沒有保留 `main` 的授權檢查；最終 merge commit 仍沒有檢查。測試應能指出授權回歸。

**標準答案：**恰有一項 P1 授權問題。證據鏈要指出 `main` parent 原有的 owner 檢查、另一側新增的付款流程，以及最終 merge tree 仍可由不同帳號觸發扣款。finding 應引用 merge parent 和最終審查版本，不能只憑衝突標記推論。

**誤報控制：**若最終 commit 已保留授權檢查，不能因 merge patch 曾出現該區塊而回報。

## 案例 2：沒有文字衝突，但跨分支 API 不相容

**共同起點：**

```typescript
export function charge(amount: number): Receipt { /* ... */ }
```

**兩端變更：**`main` 將公開介面改成 `charge(request: PaymentRequest)`，並更新同一分支內的呼叫端。`feature` 在另一個檔案新增呼叫 `charge(order.total)`。兩邊修改不同檔案，因此 `git merge-tree --write-tree` 可乾淨合併，但整合 tree 仍有舊呼叫簽章。

**標準答案：**一項 P1 相容性問題。以 `main` 的新介面和 `merge-preview` 的呼叫端證明型別不相容；以預覽版本指出受影響路徑。即使沒有執行編譯器，也要將情境標成依程式推導，不能聲稱測試已失敗。

**誤報控制：**若 `feature` 呼叫端已使用新的 request 物件，介面變更本身不構成問題。

## 案例 3：後續提交已修復 merge commit 的授權回歸

**建置情境：**先建立案例 1 的錯誤 merge commit，再於 `feature` 後續 commit 加回 owner 檢查和拒絕未授權請求的測試。將後續修復 commit 作為審查 head。

**標準答案：**不回報案例 1 的授權 finding；若沒有其他缺陷，結果為 `未發現具體問題`、建議 `可以合併`。報告可記錄 merge commit 曾有差異，但要以最終 head 的修復內容為準。

**失敗條件：**把已修好的問題列為 finding，或引用舊 merge tree 當作目前仍存在的行為。

## 案例 4：功能分支沒有引入基礎版本既有缺陷

**建置情境：**共同起點和 `main` 都有一個既有的金額四捨五入缺陷。`feature` 只新增付款稽核記錄，沒有改動金額計算、呼叫端或相關設定。

**標準答案：**不把四捨五入缺陷歸因於此次變更；若新增稽核流程本身正確，結果為 `未發現具體問題`。基礎版本檢查應能解釋為何該缺陷不是本次引入。

**失敗條件：**只因 head 中看見已知壞程式碼，就建立本次變更 finding。

## 案例 5：安全重構保留原有授權語意

**建置情境：**`feature` 將 inline 的 owner 檢查移入共用 `requireOrderAccess` 函式；函式仍拒絕非擁有者，呼叫端在付款前呼叫它，並保留原有拒絕測試。

**標準答案：**授權語意等價，不建立安全性 finding；在完整檢查其他相關行為後，結果為 `未發現具體問題`。

**誤報控制：**只因驗證從一個檔案移到另一個檔案、或變數名稱改變，不能推論授權缺失。

## 案例 6：大變更留下未覆蓋路徑

**建置情境：**建立至少 50 個受影響檔案；假設本次人工審查只逐檔完成前 20 個，其餘 30 個尚未檢查。

**標準答案：**`coverage` 必須列出所有 manifest 變更路徑與 rename 的新舊路徑；未檢查路徑標為 `not-reviewed` 並寫明原因。驗證器應輸出 `審查未完成` 和 `需補做審查`，不得以已檢查的 20 個檔案推論整體通過，也不得默默省略其餘 30 個檔案。

## 通過準則

案例 1、2 必須抓到問題並引用固定版本的正確證據；案例 3、4、5 不得產生對應誤報；案例 6 必須保留逐檔缺口並維持未完成狀態。所有案例的問題編號、嚴重度、報告數量和合併建議也必須一致。測試者應保存審查報告並註記 Skill／模型版本與執行日期，供後續比較漏報和誤報變化。
